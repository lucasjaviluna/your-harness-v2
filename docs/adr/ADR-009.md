# ADR-009 — Verification, Evidence and Post-Execution Interpretation

- **Status:** Proposed
- **Date:** 2026-09-13

## Context

ADR-004 establishes that `RuntimeResult` is runtime output, not engineering evidence.
ADR-007 establishes that post-execution guardrails interpret results but do not
automatically advance aggregate state. YH now records operational `ExecutionTrace`
entries that link a Change provenance, Specification, WorkItem and RuntimeResult.

YH needs a model that turns execution observations into reviewable verification
material while preserving the difference between:

- a runtime completing a request;
- a test or other artifact being observed;
- evidence supporting a particular Requirement or Scenario; and
- an authorized engineering completion decision.

## Decision

### 1. RuntimeResult is an observation, not a verification outcome

`RuntimeResult` remains an immutable runtime-level observation carried by
`ExecutionTrace`. Its status is interpreted into a neutral post-execution disposition:

| RuntimeResult status | Initial disposition |
| --- | --- |
| `completed` | `pending-verification` |
| `failed` | `requires-investigation` |
| `cancelled` | `requires-investigation` |

This disposition does not mark a WorkItem done, blocked or cancelled. It tells
Application what verification work or review is still required.

### 2. Evidence is a typed, immutable claim tied to a subject

Evidence is an Application-level operational record. A minimum evidence item carries:

```text
Evidence
├── id
├── executionTraceId
├── subject: RequirementId | ScenarioId | neutral artifact reference
├── kind: test-result | command-result | artifact-digest | review-note | attestation
├── outcome: passed | failed | inconclusive
├── locator / digest / summary
└── capturedAt
```

An evidence item records what was observed and where it can be inspected. It does not
declare a Specification approved, authorize a release, or mutate a WorkItem.

### 3. Verification evaluates criteria against approved behavior

A `VerificationPlan` selects approved Requirements and Scenarios and defines the
evidence expected for each criterion. A `VerificationReport` evaluates that plan
against collected evidence with one of these results:

```text
verified | failed | inconclusive | requires-human-review
```

`verified` means the selected criteria have sufficient evidence according to the
plan. It is not synonymous with completed engineering work, because scope, design
deviations, release conditions and human approvals may still matter.

### 4. Completion authorization is separate from verification

After a verification report, an authorized Application/Core action may:

```text
authorize completion | request rework | require further review
```

Only an explicit completion authorization may call the existing `WorkItem.complete()`
transition. The authorizer, HITM requirements and persistence model remain open.

### 5. Traceability is preserved without expanding the Runtime Boundary

The proposed operational chain is:

```text
Change/task provenance + Specification + WorkItem
                      ↓
                ExecutionTrace
                      ↓
                 RuntimeResult
                      ↓
          Evidence + VerificationReport
                      ↓
          explicit completion authorization
```

Provider-specific references remain opaque `SddProvenance`. The Runtime receives no
VerificationPlan, Evidence, report or authorization type unless a future neutral
runtime capability is intentionally designed.

## Consequences

### Positive

- Prevents successful agent output from being mistaken for proof of correctness.
- Connects verification to approved Requirements and Scenarios rather than only to
  generic test output.
- Makes evidence inspectable and traceable to an execution.
- Preserves Human-in-the-Middle authority for completion.

### Trade-offs

- Verification adds operational records and explicit evaluation work.
- A completed runtime can remain pending verification.
- Evidence retention, artifact storage and evaluator implementation require later
  infrastructure decisions.

## Explicit Non-Goals

This ADR does not yet implement:

- automatic test execution, artifact collection or model-based judging;
- a universal evidence schema for every tool or provider;
- automatic WorkItem transitions;
- a release gate, approval UI or full HITM workflow;
- hashing/signing or external artifact storage for evidence/reports;
- RAG or retrieval over evidence.

## Future Decisions

1. Criterion selection and minimum-evidence rules per project.
2. Durable local storage and artifact locator/digest strategy.
3. Human authorization policy and WorkItem completion use case.
4. Tool/runtime integration for collecting evidence under `ExecutionEnvironment`.

## Implementation note

Application now provides `Evidence`, `VerificationPlan`, `VerificationReport` and
repository contracts, plus `RecordEvidenceUseCase`, a deterministic evaluator and an
in-memory Evidence adapter. Local infrastructure persists all three operational records,
and Evidence registration verifies that the referenced `ExecutionTrace` exists. This
is a partial implementation of the proposed design; it does not authorize completion.

## Decision Summary

YH will interpret `RuntimeResult` as an execution observation. Typed evidence and
verification reports evaluate approved requirements and scenarios, while explicit
authorization — never runtime success alone — controls engineering completion.
