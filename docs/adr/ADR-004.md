# ADR-004 — Runtime Boundary and Execution Contract

- **Status:** Proposed
- **Date:** 2026-09-09
- **Decision:** YH will isolate the Engineering Core from concrete agent execution through an Application-level Runtime Boundary. Execution will cross that boundary through a minimal `ExecutionRequest` and return a `RuntimeResult`. Concrete runtimes such as the native YH runtime or Pi will remain implementation details behind adapters.

## Context

ADR-002 established the architectural separation between the Engineering Core and Agent Runtime.

ADR-003 established the Engineering Specification Model, where Specifications contain Requirements and Scenarios and belong to the Engineering Core.

YH already contains runtime-oriented infrastructure including `Harness`, `WorkflowEngine`, `AgentRunner`, `AIManager`, `MCPManager`, `PromptBuilder`, runtime sessions and events, and AI providers and tools. These components are execution machinery, not the architectural boundary between engineering management and agent execution.

In particular:

- `AIManager` is too low-level to represent an entire runtime.
- `AgentRunner` represents one implementation of an agent loop.
- `Harness` currently orchestrates runtime capabilities but exposes implementation-oriented concepts.
- Pi provides its own runtime/session/event model through `AgentSession` and related APIs.

If YH directly models its Engineering Core around any of these implementations, replacing the runtime would require changes throughout the Engineering Core.

YH also needs to support execution by different mechanisms: manually, through the native YH runtime, through Pi, through another runtime, or through a workflow/external mechanism.

Therefore a WorkItem must request execution without being coupled to a particular runtime.

## Decision

YH will introduce a conceptual **Runtime Boundary** at the Application layer.

```text
Engineering Core
        |
        v
Application Use Case
        |
        v
Runtime Boundary / Port
        |
        +----------------------+
        |                      |
        v                      v
Native Runtime Adapter     Pi Runtime Adapter
        |                      |
        v                      v
YH Runtime Machinery       Pi AgentSession
```

The Engineering Core does not depend on Pi, `AgentSession`, `AgentRunner`, `AIManager`, `WorkflowEngine`, or other concrete runtime implementation details.

## 1. Runtime Boundary is an Application concern

The Runtime Boundary belongs conceptually to the Application layer because it expresses what the application needs from an execution runtime.

It must not be placed in the Domain merely because execution is related to WorkItems.

The Domain remains concerned with engineering concepts and state.

Conceptually:

```text
packages/application/src/runtime/
    runtime-port.ts
```

The exact implementation and file structure are not decided by this ADR.

## 2. ExecutionRequest is the input contract

YH will use a minimal `ExecutionRequest` to cross the Runtime Boundary.

```text
ExecutionRequest
├── objective
├── workspace
├── engineeringContext
└── executionConstraints
```

`objective` describes the objective the runtime is being asked to accomplish; it is not necessarily identical to the complete WorkItem aggregate.

`workspace` identifies the workspace in which execution should occur. For a runtime such as Pi, this can naturally map to its working directory / `cwd`.

`engineeringContext` contains relevant engineering knowledge selected by YH for the execution. It may include knowledge, Requirements, Scenarios, and engineering constraints. The request does not expose the mechanism used to obtain that context. A future RAG system may contribute retrieved knowledge, but RAG-specific concepts do not belong in the request model.

`executionConstraints` contains constraints or instructions specific to the execution operation. These are distinct from engineering requirements and engineering constraints.

Guardrails may enforce these constraints, but guardrails themselves are not part of the request model.

## 3. Do not pass Domain aggregates across the boundary

The Runtime Boundary must not require concrete domain aggregates such as `WorkItem`, `Specification`, `Intent`, `Review`, or `Release` as its runtime API.

Instead, the Application layer contextualizes the required information into the execution request.

The runtime receives what it needs to execute, not ownership of YH's engineering state.

## 4. RuntimeResult is an integration result

The runtime returns a minimal `RuntimeResult`.

```text
RuntimeResult
├── status
├── summary
├── runtimeSessionId
├── timestamps
└── failure
```

The result describes what happened from the runtime's perspective. It does not directly change Engineering Core state.

For example, a runtime may report that implementation completed and tests passed. YH must not interpret that automatically as `WorkItem = Done`.

The result must pass through application-level engineering interpretation and, where required, verification and governance.

```text
Runtime
   |
   v
RuntimeResult
   |
   v
Application
   |
   v
Engineering interpretation
   |
   +--> verification / evidence
   |
   +--> governance / HITM
   |
   v
Engineering State
```

## 5. Runtime session identity is runtime state

A runtime may maintain its own session, including conversation history, tool execution history, compaction state, session tree/fork state, and runtime-specific events.

YH may retain a reference such as `runtimeSessionId` when useful for continuation, diagnostics, or traceability.

The runtime session itself is not an Engineering Core aggregate.

```text
Engineering State
    ≠
Runtime State
```

A runtime session is not a WorkItem. A tool call is not an engineering state transition. A model response is not an engineering decision.

## 6. Streaming is a runtime observation mechanism

The Runtime Boundary should not mirror the complete event model of a concrete runtime.

If Pi exposes detailed `AgentSession` events, YH should not reproduce every Pi event as a YH domain event.

Streaming and runtime events are runtime observation mechanisms. A future Application API may expose a generic observer/subscription mechanism, but the exact streaming API remains undecided.

## 7. Workflow remains an execution strategy

A `Workflow` is not a required property of a `WorkItem`.

```text
WorkItem
    |
    v
Execution Request
    |
    v
Runtime Boundary
    |
    v
Workflow / execution strategy
    |
    v
Runtime
```

or, when no workflow is needed:

```text
WorkItem
    |
    v
Execution Request
    |
    v
Runtime
```

A WorkItem can therefore be executed without requiring a `workflowId`.

## 8. Runtime adapters isolate concrete implementations

Concrete runtimes are hidden behind adapters.

```text
Runtime Port
    |
    +-- NativeRuntimeAdapter
    |
    +-- PiRuntimeAdapter
    |
    +-- OtherRuntimeAdapter
```

The Pi adapter may internally use `AgentSession`, `ModelRegistry`, `ResourceLoader`, extensions, Pi tools, and Pi events, but none of these concepts cross into the Engineering Core.

Likewise, the native adapter may internally use `Harness`, `WorkflowEngine`, `AgentRunner`, `AIManager`, `MCPManager`, and `ToolExecutor` without exposing those concepts through the Engineering Core.

## 9. Pi is an implementation option, not an architectural dependency

Pi is treated as a candidate runtime implementation.

YH must remain valid if Pi is not used, Pi is replaced, the native runtime is used, or multiple runtimes coexist.

Therefore the Runtime Boundary must not contain Pi-specific types, imports, lifecycle semantics, persistence structures, or event models.

```text
Application
    |
    v
Runtime Port
    ^
    |
Runtime Adapter
    |
    +--> Pi
    +--> Native Runtime
```

## 10. Runtime output does not equal Engineering Evidence

Runtime output can include command output, test output, tool results, agent messages, workflow results, errors, and generated artifacts.

These are runtime outputs. They may later become engineering evidence, but only through an explicit engineering interpretation/verification process.

This ADR deliberately does not define the Evidence or Verification domain model.

## 11. Governance and HITM remain outside the runtime

The runtime can support pause, resume, confirmation, approval callbacks, and interruption. However, the runtime does not decide which engineering actions require approval.

Governance and Human-in-the-Middle requirements remain Engineering Core concerns.

A runtime confirmation is not automatically an engineering approval.

## Consequences

### Positive

- The Engineering Core becomes independent from concrete agent runtimes.
- Pi can be adopted without redesigning domain concepts.
- The existing native runtime can remain useful behind an adapter.
- Runtime state and engineering state remain separate.
- WorkItems remain independent from Workflow implementation.
- Runtime results cannot silently mutate engineering state.
- Future RAG can provide EngineeringContext without coupling the runtime to the retrieval implementation.
- Future guardrails can be placed at appropriate boundaries without making them part of the runtime contract.
- Runtime-specific streaming/event models remain isolated.

### Negative

- An adapter layer introduces additional translation code.
- Execution results require an explicit interpretation step.
- Some runtime capabilities may not map perfectly to the minimal common contract.
- Advanced runtime features may require optional capabilities rather than expanding the core contract.

## What this ADR does not decide

This ADR deliberately does not decide:

- the final TypeScript definition of `RuntimePort`;
- the exact `ExecutionRequest` TypeScript type;
- the exact `RuntimeResult` TypeScript type;
- runtime capability negotiation;
- runtime selection policy;
- Pi integration implementation;
- native runtime adapter implementation;
- streaming API details;
- EngineeringContext implementation;
- RAG architecture;
- guardrail architecture;
- Verification/Evidence model;
- runtime persistence;
- session storage strategy;
- whether workflows are ultimately implemented above or inside a specific runtime.

## Decision summary

YH will isolate Engineering Core from concrete agent execution through an Application-level Runtime Boundary.

The minimal conceptual contract is:

```text
ExecutionRequest
        |
        v
Runtime Port
        |
        v
Runtime
        |
        v
RuntimeResult
```

The runtime is responsible for execution.

YH remains responsible for engineering state, interpretation, verification, governance, and authoritative engineering knowledge.

Concrete runtimes such as Pi and the existing native YH runtime remain replaceable implementation details behind this boundary.
