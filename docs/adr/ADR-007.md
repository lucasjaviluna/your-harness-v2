# ADR-007 — Layered Engineering Guardrails

- **Status:** Proposed
- **Date:** 2026-09-12

## Context

YH is specification-driven and keeps governance in the Engineering Core. ADR-002,
ADR-004, and ADR-005 establish that a Runtime executes an `ExecutionRequest` but
does not own engineering approval, state transitions, or interpretation of results.

Guardrails therefore cannot be one generic boolean check or a runtime-only concern.
They protect different kinds of authority at different points: required behavior,
technical design, execution eligibility, runtime operation, and future result
interpretation.

The current `ContextAssembler` already rejects a Specification that is not approved
before it becomes an `EngineeringContext`. That is a useful first safeguard, but it
is currently an implicit policy rather than a named, composable guardrail.

## Decision

### 1. Guardrails are Engineering Core policy, enforced at boundaries

A guardrail is a policy that decides whether engineering work may advance, requires
human review, or must stop. The Engineering Core owns the policy and its authority.
Application use cases and Runtime adapters may enforce the policy at their respective
boundaries, but enforcement must not move the authority to the Runtime.

Guardrails produce one of three conceptual outcomes:

```text
allow | deny (reason) | require human review (reason)
```

They do not automatically change aggregate state. Any approval, completion, or other
engineering transition remains an explicit Engineering Core action.

### 2. Guardrails are layered by responsibility

```text
Specification guardrails
  └── correctness and authority of WHAT is required

Design guardrails
  └── coherence of HOW with approved behavior and deviation handling

Execution guardrails
  └── whether a particular work item may create an ExecutionRequest

Runtime guardrails
  └── technical operating envelope while an approved request executes

Post-execution guardrails
  └── future interpretation, verification, evidence, and state transitions
```

The layers are complementary. Passing a runtime constraint does not satisfy a
Specification or Design guardrail, and a runtime confirmation is not an engineering
approval.

### 3. Responsibilities of each layer

| Layer | Owner | Examples | Explicit boundary |
|---|---|---|---|
| Specification | Domain / Engineering Core | normative statement, scenario structure, lifecycle approval | determines whether behavior is authoritative |
| Design | Engineering Core / Application | design applicability, approved deviations, design-to-specification coherence | design cannot silently override requirements |
| Execution | Application | approved Specification, valid work scope, future SDD traceability, HITM requirements | decides whether an `ExecutionRequest` may be built |
| Runtime | runtime adapter / host, under Core policy | workspace, tools, execution constraints, interruption | enforces an operating envelope but does not govern engineering state |
| Post-execution | Application / Engineering Core | future verification, evidence review, completion authorization | interprets `RuntimeResult`; runtime output is not proof of completion |

### 4. The first concrete guardrail is execution eligibility

The current rule—only an approved Specification can become an
`EngineeringContext`—is the initial execution-eligibility safeguard. It is now
extracted into an Application-level `ExecutionEligibilityPolicy` because it composes
with a second concrete condition.

When SDD mode and `SddProvider` material exist, that policy may additionally require
approved and traceable specification support for the requested work. It must inspect
normalized Application data, not provider types or runtime objects.

### Implementation status

`ExecutionEligibilityPolicy` is implemented in Application. It denies execution for
a Specification that is not approved and, when configured with
`requireSddChangeTraceability`, for an execution without neutral Change provenance.
`ExecuteWorkItemUseCase` enforces it before creating `ExecutionRequest`. The policy
does not yet have project-level configuration, design checks, HITM outcomes or
post-execution evidence rules.

### 5. Runtime constraints remain distinct from guardrails

`ExecutionRequest.executionConstraints` are instructions for the runtime's technical
operating envelope. They are not Engineering Core governance rules and must not be
used to authorize a work item, accept a design deviation, or mark work complete.

The runtime may report a constraint violation through `RuntimeResult`. Application
then decides whether any engineering action or human review is required.

## Consequences

### Positive

- Makes governance composable without collapsing it into the Runtime.
- Gives each future policy a clear authority and enforcement boundary.
- Allows SDD traceability to strengthen execution eligibility without coupling YH to
  a provider.
- Preserves HITM for decisions that require it.
- Establishes a path from the existing approval check to explicit policy objects only
  when composition becomes necessary.

### Trade-offs

- A single engineering action may eventually be evaluated by more than one policy.
- Policy failures need clear user-facing explanations and auditability.
- The early system will intentionally have only a small subset of the layers active.

## Explicit Non-Goals

This ADR does not decide:

- project-level configuration for enabling or disabling eligibility rules;
- which design artifacts are authoritative or how they are stored;
- per-provider SDD policies;
- a configuration syntax for enabling or disabling policies;
- tool permissions, sandbox technology, network policy, or secrets management;
- verification or evidence aggregates;
- automatic WorkItem transitions;
- a complete HITM workflow.

## Relationship with Previous ADRs

- **ADR-002:** Engineering governance remains on the Engineering Core side of the
  Runtime Boundary.
- **ADR-003:** Specification guardrails protect the authority of normative
  Requirements and Scenarios.
- **ADR-004 / ADR-005:** the Runtime receives neutral execution data; a successful
  runtime result is not an engineering decision.
- **ADR-006:** SDD provenance can later participate in execution eligibility without
  exposing provider artifacts to the Runtime.

## Future Decisions

1. Define project-level configuration and richer SDD traceability criteria.
2. Define the authority and lifecycle of Design material.
3. Define Verification and Evidence before enabling post-execution completion rules.
4. Define technical runtime operating policies for concrete adapters.

## Decision Summary

YH will treat guardrails as layered Engineering Core policy. Runtime adapters enforce
only the approved operating envelope; they do not govern specifications, designs,
work items, approvals, or completion.
