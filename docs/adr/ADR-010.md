# ADR-010 — Ciclo de vida SDD neutral

- **Estado:** Proposed
- **Fecha:** 2026-09-14
- **Decisión:** definir dos ciclos coordinados, pero independientes: el ciclo de vida de una `Specification` y el ciclo de vida de un `Change`.

## Contexto

your-harness necesita orquestar tareas SDD de distintos proveedores, comenzando por OpenSpec. El `TaskOrchestrator` no debe interpretar directamente estados o archivos propios de un proveedor. Antes de construirlo necesitamos un lenguaje neutral para expresar qué material está siendo elaborado, revisado, aprobado, ejecutado y verificado.

El dominio ya tiene un ciclo de vida para `Specification`:

```text
Draft → InReview → Approved → Superseded
  └──────────────────────────────────┘
             → Archived (administrativo)
```

Ese ciclo no describe por sí solo la evolución de un cambio de ingeniería ni el estado de sus tareas. Tampoco debe confundirse la aprobación de una Specification con la autorización HITM para ejecutar o completar un WorkItem.

## Propuesta

### 1. Ciclo de vida de Specification

Se conserva el ciclo existente como semántica de autoridad sobre el **WHAT**:

```text
Draft → InReview → Approved → Superseded → Archived
```

Reglas iniciales:

- `Draft` permite elaborar o modificar requisitos y escenarios.
- `InReview` representa una especificación lista para revisión.
- `Approved` habilita su uso como contexto de ingeniería, sujeto a los demás guardrails.
- `Superseded` indica que una versión posterior la reemplazó.
- `Archived` es un estado administrativo terminal de conservación histórica; no forma parte de la secuencia normal de aprobación y puede aplicarse a cualquier estado no archivado según la regla actual de Domain.

Una Specification aprobada no autoriza por sí sola la ejecución, no completa un WorkItem y no transforma automáticamente un Change en evidencia.

### 2. Ciclo de vida de Change

Se propone el siguiente ciclo neutral para una evolución de ingeniería:

```text
Proposed → Approved → Executing → VerificationPending → Completed
    │           │          │                │
    └───────────┴──────────┴────────────────┴→ Withdrawn
```

Significado de los estados:

- `Proposed`: el cambio existe como propuesta, con rationale y material asociado.
- `Approved`: el cambio fue aceptado para ser ejecutado; la autoridad y aprobación se registran como governance de your-harness.
- `Executing`: existe un alcance de ejecución materializado y el trabajo está siendo desarrollado.
- `VerificationPending`: hubo una ejecución, pero los resultados todavía requieren verificación y evidencia.
- `Completed`: el cambio fue verificado y su cierre fue autorizado explícitamente.
- `Withdrawn`: el cambio dejó de estar vigente sin completar el flujo.

`Completed` no debe alcanzarse sólo por marcar todas las tareas del proveedor como completas. Requiere el flujo de Verification/Evidence y la autorización HITM definida por Application.

### 3. Tareas del Change

Las tareas del proveedor se proyectan como material operativo, no como aggregates de Domain. Su estado puede conservar inicialmente sólo:

```text
Pending | Completed
```

Si un proveedor expone estados más ricos, se conserva el estado nativo mediante provenance/opacidad y se normaliza sólo lo necesario para la elegibilidad y la observabilidad.

### 4. Relación entre los ciclos

La relación propuesta es:

```text
Specification Approved
        +
Change Approved
        +
HITM execution approval
        ↓
Execution scope → Runtime execution → Verification/Evidence
                                      ↓
                              HITM completion authorization
                                      ↓
                                Change Completed
```

Estas condiciones son coordinadas por Application y, en el futuro, por el orquestador. El proveedor SDD sigue siendo dueño de sus artefactos y no recibe aggregates de Domain ni decisiones internas del Runtime.

## Decisiones que quedan abiertas

1. Si `Approved` en Change requiere siempre una aprobación HITM propia o puede representar sólo el estado nativo del proveedor.
2. Si `Executing` debe ser una transición explícita previa a la primera invocación del Runtime o una observación derivada de una ExecutionTrace.
3. Si `VerificationPending` pertenece al ciclo neutral de Change o debe permanecer exclusivamente en el modelo de Application.
4. Si `Withdrawn` basta como estado terminal o necesitamos distinguir `Rejected`, `Cancelled` y `Superseded`.
5. Qué estados nativos de OpenSpec se pueden mapear de forma confiable y cuáles deben permanecer opacos.

## Resolución recomendada para la primera implementación

Para evitar que el proveedor se convierta accidentalmente en el dueño del workflow de your-harness, se propone esta separación:

| Responsabilidad | Dueño | Representación |
|---|---|---|
| Estado nativo de Specification/Change/tarea | Proveedor SDD | Proyección neutral más provenance opaca |
| Aprobación y elegibilidad de Specification | Application/Domain | `SpecificationStatus` y políticas existentes |
| Aprobación de Change para ejecución | Application | Decisión HITM auditable |
| `Executing` | Application | Estado operacional asociado al Change y a la ejecución |
| `VerificationPending` | Application | Resultado pendiente de Verification/Evidence |
| `Completed` | Application | Verification satisfactoria más CompletionAuthorization |

En consecuencia, el proveedor no debe fingir que conoce `Executing`, `VerificationPending` o `Completed` si su formato no los expresa. Esos estados representan el ciclo gobernado por your-harness. El adapter puede informar el estado nativo cuando exista y conservarlo como dato de provenance.

La primera versión del contrato neutral debería exponer estados descriptivos y no operaciones de transición. Las transiciones serán responsabilidad de casos de uso de Application, una vez que se defina el límite de escritura y sincronización del proveedor en el punto 3 del plan.

## Invariantes propuestas

Estas reglas deben mantenerse aunque cambie OpenSpec u otro proveedor:

1. Una Specification sólo puede ser usada como autoridad del WHAT cuando Application la considera aprobada.
2. La aprobación de una Specification no implica aprobación de ningún Change.
3. Un Change no puede considerarse `Completed` sólo porque sus tareas estén marcadas como completadas.
4. `Executing` debe estar respaldado por una selección de alcance, una Specification aprobada y las autorizaciones HITM requeridas.
5. `VerificationPending` significa que existe una ejecución observable, pero todavía no una autorización de completitud.
6. Cualquier cambio en la proyección aprobada debe invalidar el snapshot/digest y exigir rebind o reautorización.
7. Un estado nativo que el proveedor no pueda demostrar no debe inferirse a partir de una traza de your-harness.
8. Cada transición gobernada por Application debe conservar actor, rol, motivo, instante y referencias de provenance suficientes para auditoría.

## Borrador de vocabulario contractual

Como siguiente paso de implementación, se propone introducir vocabulario neutral separado por responsabilidad:

- `SpecificationStatus`: reutilizar el enum existente de Domain.
- `SddChangeStatus`: proyección descriptiva del estado del Change cuando el proveedor pueda mapearlo; incluir `unknown` cuando no exista una correspondencia confiable.
- `SddTaskStatus`: comenzar con `pending`, `completed` y `unknown`; conservar el estado nativo fuera del conjunto normalizado.
- `GovernedChangeStatus`: estado operacional de your-harness (`proposed`, `approved`, `executing`, `verification-pending`, `completed`, `withdrawn`), propiedad de Application y no del proveedor.

La diferencia entre `SddChangeStatus` y `GovernedChangeStatus` es deliberada: el primero describe lo que el proveedor afirma; el segundo describe lo que your-harness ha autorizado y observado.

## Consecuencias

- El `SddProvider` podrá proyectar estado neutral sin acoplar Application a OpenSpec.
- La aprobación de Specification, la aprobación de Change y la autorización HITM quedan conceptualmente separadas.
- El futuro `TaskOrchestrator` coordinará transiciones y guardrails, pero no será dueño de la semántica de los artefactos.
- La implementación debe evitar que una proyección read-only finja que OpenSpec ya soporta escritura o lifecycle completo.
