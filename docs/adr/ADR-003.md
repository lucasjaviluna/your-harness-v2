# ADR-003 — Engineering Specification Model

- **Status:** Proposed
- **Date:** 2026-09-09
- **Decision:** Engineering specifications are modeled as domain knowledge composed of normative Requirements and their Scenarios. Specification Engines such as OpenSpec may produce or manage specifications, but their concrete artifacts and formats are not part of the YH domain model.

## Context

Your Harness needs a specification model that supports a future Specification-Driven Development (SDD) process.

The current `Specification` domain concept establishes a specification as engineering knowledge that can become part of the project's source of truth, with its own lifecycle. However, the current model is intentionally minimal and does not yet represent the behavioral content of a specification.

OpenSpec provides a useful reference for this problem. Its spec-driven workflow separates:

- `proposal` — why a change is needed;
- `specs` — what behavior is required;
- `design` — how the change should be implemented;
- `tasks` — implementation work.

Within a specification, OpenSpec represents behavior through Requirements and Scenarios. Requirements express normative behavior, while Scenarios describe observable conditions and expected outcomes.

YH must be able to follow these semantics without making OpenSpec a mandatory dependency or turning OpenSpec's file structure into YH's domain model.

This distinction is also necessary to preserve the architectural separation established by ADR-001 (Specification Engine Abstraction) and ADR-002 (Engineering Core and Agent Runtime Boundary).

## Decision

YH will model an Engineering Specification as domain knowledge whose behavioral content is expressed through **Requirements** and **Scenarios**.

The conceptual model is:

```text
Specification
    |
    +-- Requirement
    |      |
    |      +-- Scenario
    |      +-- Scenario
    |
    +-- Requirement
           |
           +-- Scenario
```

### 1. Specification is an Engineering Core concept

`Specification` belongs to the Engineering Core.

It represents authoritative engineering knowledge describing desired or required system behavior.

The Specification lifecycle remains independent from any concrete Specification Engine or runtime.

### 2. Requirement is the normative unit of behavior

A `Requirement` represents a specific behavioral obligation of the system.

Conceptually it contains:

```text
Requirement
├── identity
├── name
├── normative statement
└── scenarios
```

The normative statement describes what the system SHALL or MUST do.

The model should preserve this semantic distinction rather than reducing requirements to unstructured strings.

### 3. Scenario describes observable behavior

A `Scenario` represents an explicit condition and expected behavior associated with a Requirement.

Conceptually:

```text
Scenario
├── condition / WHEN
└── expected behavior / THEN
```

A Scenario is not an implementation instruction. It describes behavior that can later be used as a basis for validation or verification.

### 4. WHAT, HOW and IMPLEMENTATION remain separate

YH will preserve the following conceptual separation:

```text
WHAT
Specification
└── Requirement
    └── Scenario

HOW
Design / Engineering Decisions

IMPLEMENTATION
WorkItem / implementation tasks
```

A Specification must not become a container for design documents or implementation checklists.

Likewise, a `WorkItem` is not considered equivalent to an OpenSpec task.

### 5. Specification Engines remain replaceable

OpenSpec may be used as a Specification Engine, but YH will not expose OpenSpec-specific concepts in its domain model.

Conceptually:

```text
Specification Engine
        |
        +-- OpenSpec
        +-- Other SDD framework
        +-- Future YH-native implementation
        |
        v
YH Specification Model
        |
        +-- Requirement
        |      +-- Scenario
        |
        v
Engineering Core
```

A concrete engine is responsible for translating its own artifacts and representation into the YH conceptual model where integration requires such a representation.

YH therefore does not model fields such as:

```text
openspec
proposal.md
spec.md
design.md
tasks.md
```

as intrinsic properties of the domain `Specification`.

### 6. OpenSpec artifacts map to different engineering concepts

Where OpenSpec is used, its concepts are interpreted according to their semantic responsibility rather than treated as one aggregate.

Conceptually:

| OpenSpec concept | YH conceptual responsibility |
|---|---|
| `proposal.md` | Intent/change rationale |
| `spec.md` | Specification |
| Requirement | Requirement |
| Scenario | Scenario |
| `design.md` | Design / technical decisions |
| `tasks.md` | Implementation work |
| `apply` | Execution |

This is a semantic mapping, not a requirement that YH reproduce OpenSpec's files or directory structure.

### 7. Traceability is a first-class architectural concern

The model should support a future engineering traceability chain:

```text
Intent
  |
  v
Specification
  |
  v
Requirement
  |
  v
Scenario
  |
  v
WorkItem
  |
  v
Implementation
  |
  v
Verification
```

This ADR does not introduce `Verification` or `Evidence` as domain aggregates. Their design remains a future decision.

The purpose of this traceability is to allow YH to relate engineering intent to expected behavior, implementation work, and eventual validation.

### 8. Engineering Context consumes specifications

The Specification remains the authoritative source of requirements.

A future `EngineeringContext` may contain a contextualized representation of relevant Requirements and Scenarios for a specific execution.

Conceptually:

```text
Specification
    |
    v
Requirement + Scenario
    |
    v
Engineering Context
    |
    v
Execution Request
    |
    v
Runtime Boundary
```

`EngineeringContext` is not the owner of the Specification and does not replace it.

Likewise, retrieval mechanisms such as future RAG are mechanisms for selecting relevant engineering knowledge; they do not become part of the Specification model.

## Consequences

### Positive

- YH can support SDD without coupling the domain to OpenSpec.
- Requirements retain normative semantics instead of becoming plain text.
- Scenarios provide explicit behavioral expectations that can later support verification.
- The distinction between WHAT, HOW and implementation remains clear.
- OpenSpec can be adopted, replaced, or supplemented without redesigning the Engineering Core.
- Future RAG/context systems can retrieve structured engineering knowledge without becoming the source of truth.
- The model supports traceability from Intent through implementation and future verification.

### Negative

- The domain model becomes richer than the current minimal `Specification`.
- A Specification Engine adapter will eventually need a translation/mapping layer.
- Versioning, identity, change/delta semantics, and persistence details still need to be defined.
- Different SDD frameworks may expose semantics that do not map perfectly to the normalized YH model.

## What this ADR does not decide

This ADR deliberately does not decide:

- the concrete TypeScript implementation of `Requirement`;
- the concrete TypeScript implementation of `Scenario`;
- the persistence model;
- the physical file format of specifications;
- whether specifications are stored as Markdown, JSON, YAML, or another representation;
- the final OpenSpec adapter design;
- the final SDD framework selection;
- the design of `EngineeringContext`;
- the final `ExecutionRequest` contract;
- the design of Verification or Evidence;
- the RAG implementation;
- the guardrail implementation.

Those decisions should be made only when a concrete use case requires them.

## Relationship with previous decisions

### ADR-001 — Specification Engine Abstraction

ADR-001 establishes that the specification mechanism is replaceable.

This ADR defines the normalized domain concept that a Specification Engine can produce or manage.

```text
Specification Engine
        |
        v
YH Specification
```

### ADR-002 — Engineering Core and Agent Runtime Boundary

ADR-002 establishes that engineering knowledge and engineering governance belong to the Engineering Core, while agent execution belongs to the Runtime.

This ADR places Specification, Requirement and Scenario on the Engineering Core side of that boundary.

```text
Engineering Core
    |
    +-- Specification
    |     +-- Requirement
    |           +-- Scenario
    |
    v
Runtime Boundary
    |
    +-- Native Runtime
    +-- Pi Runtime
```

## Decision summary

YH will treat a Specification as **structured engineering knowledge about required behavior**, with Requirements and Scenarios as its core semantic elements.

OpenSpec is a possible Specification Engine, not the YH Specification domain model.

The architectural relationship is therefore:

```text
Specification Engine
        |
        v
Specification
        |
        +-- Requirement
        |      |
        |      +-- Scenario
        |
        v
Engineering Context
        |
        v
Execution Request
        |
        v
Runtime Boundary
        |
        +-- Native Runtime
        +-- Pi
```
