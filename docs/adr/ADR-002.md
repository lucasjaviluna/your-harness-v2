# ADR-002 — Agent Runtime Boundary

**Document ID:** YH-ADR-002
**Version:** 1.0.0
**Status:** Proposed
**Release:** v0.1.0 Foundation / v0.2.0 Architecture

---

# Status

Proposed

---

# Context

Your Harness is an engineering platform focused on governing the software engineering process rather than code generation alone.

The platform defines engineering concepts such as Intent, Work Item, Specification, Review and Release, together with specification-driven development, governance, traceability and Human in the Middle.

The current repository also contains implementation concerns related to agents, AI interaction, context, tools, MCP, plugins, skills and workflows.

At the same time, several external agent runtimes and coding-agent harnesses are available. Pi is one example. Pi provides capabilities such as agent execution, tool calling, sessions, model/provider integration, extensions and skills.

These capabilities overlap partially with the execution concerns that Your Harness may require.

However, coupling the engineering model of Your Harness directly to a concrete agent runtime would make the engineering platform dependent on implementation details of that runtime.

This would conflict with the architectural principles established by ADR-000 and with the decision established by ADR-001, which separates stable platform capabilities from replaceable implementations.

The project therefore needs a clear architectural boundary between:

1. the engineering model owned by Your Harness; and
2. the runtime responsible for executing AI agents.

---

# Decision

Your Harness shall maintain a conceptual and architectural boundary between the **Engineering Core** and the **Agent Runtime**.

The Engineering Core shall remain independent of any concrete agent runtime implementation.

The Agent Runtime boundary shall represent the execution capabilities required by Your Harness without prescribing a specific implementation.

The platform may integrate one or more concrete runtime implementations behind this boundary.

Possible implementations may include:

* a native Your Harness runtime;
* Pi;
* other external agent runtimes;
* future runtime implementations not yet identified.

No concrete runtime is selected by this ADR.

In particular, **Pi is not established as a mandatory dependency, core runtime or default implementation by this decision**.

Runtime selection remains an implementation and deployment concern that may be addressed by subsequent architectural decisions.

---

# Architectural Boundary

The architecture shall conceptually separate the following concerns.

## Engineering Core

Your Harness owns the engineering state and rules associated with:

* Project;
* Intent;
* Work Item;
* Specification;
* Review;
* Release;
* engineering workflows;
* governance;
* approval requirements;
* verification;
* engineering traceability;
* engineering memory.

The Engineering Core defines what engineering work is being performed, why it is being performed, what constraints apply and what constitutes an acceptable state transition.

## Agent Runtime

The Agent Runtime is responsible for execution concerns such as:

* agent execution;
* agent sessions;
* interaction with AI models;
* tool execution;
* runtime events;
* runtime context;
* model selection;
* runtime-specific extensions;
* runtime-specific skills;
* runtime-specific execution mechanisms.

The exact responsibilities of the runtime boundary remain subject to further refinement.

---

# State Separation

Your Harness shall distinguish between **Engineering State** and **Agent Runtime State**.

Engineering State includes information such as:

* Intent;
* Work Item state;
* Specification state;
* Review state;
* Release state;
* approvals;
* governance decisions;
* verification results;
* engineering artifacts;
* engineering decisions.

Agent Runtime State may include:

* conversation state;
* model state;
* tool calls;
* agent execution state;
* session state;
* runtime events;
* context-management state.

These two categories of state shall not be treated as interchangeable.

An agent session is not itself an engineering Work Item.

A tool call is not itself an engineering state transition.

Runtime state may contribute evidence to an engineering workflow, but the Engineering Core remains the authority over engineering state.

---

# Runtime Independence

The Engineering Core shall not depend directly on APIs, data structures or lifecycle semantics of a concrete runtime.

For example, application or domain code shall not require direct knowledge of:

* Pi-specific session types;
* Pi-specific agent APIs;
* Pi-specific extension APIs;
* Pi-specific persistence formats;
* Pi-specific events.

Concrete runtime integrations shall be isolated behind appropriate integration boundaries.

This allows the same engineering model to operate with different runtime implementations.

---

# Runtime Implementations

A runtime implementation may provide the execution capabilities required by the Agent Runtime boundary.

Conceptually:

```
Your Harness
      |
      v
Engineering Core
      |
      v
Agent Runtime Boundary
      |
   +--+----------------+
   |                   |
   v                   v
Pi Runtime        Native/Other Runtime
```

The architecture does not require all runtime implementations to provide identical internal capabilities.

They must instead satisfy the capabilities required by the specific integration contract defined by Your Harness.

---

# Pi Integration

Pi shall be treated as a potential Agent Runtime implementation.

This ADR does not establish:

* Pi as the core of Your Harness;
* Pi as a mandatory dependency;
* Pi as the default runtime;
* Your Harness as a Pi extension;
* Pi as the only supported runtime.

A subsequent ADR or implementation decision may evaluate Pi as a concrete runtime implementation once the Agent Runtime contract has been sufficiently defined.

---

# Rationale

The primary reason for this decision is to preserve the distinction between the **engineering system** and the **mechanism used to execute agents**.

Your Harness exists to govern software engineering.

An agent runtime exists to execute agents.

Keeping these responsibilities separate provides several benefits.

## Technology Independence

The Engineering Core can evolve without depending on a specific agent runtime.

## Runtime Choice

Users and deployments may eventually choose the runtime most appropriate for their environment.

## Replaceability

A runtime can be replaced without redesigning the engineering domain.

## Experimentation

New runtimes can be evaluated without changing the core engineering model.

## Clear Ownership

Your Harness remains the authority over engineering state, while the runtime remains responsible for execution state.

## Reduced Coupling

The platform avoids allowing a concrete runtime's concepts to leak into the domain model.

---

# Consequences

## Positive

* Engineering concepts remain independent of runtime technology.
* Pi can be evaluated without committing the project to Pi.
* Alternative runtimes remain possible.
* Runtime experimentation does not require changes to the core domain.
* Engineering state remains distinct from agent session state.
* The architecture preserves the replaceability principle already established by ADR-001.
* Future runtime integrations can be introduced incrementally.

## Trade-offs

* An additional architectural boundary must be maintained.
* Runtime integrations may require adapters or integration contracts.
* Some capabilities may need translation between YH and a concrete runtime.
* The project must explicitly define which responsibilities belong to YH and which belong to the runtime.
* Multiple runtime implementations may increase testing and compatibility requirements.

These trade-offs are accepted because runtime independence is considered more important than minimizing the initial implementation surface.

---

# Consequences for Memory

Engineering Memory and Agent Runtime Memory shall be treated as separate concepts.

Engineering Memory may contain:

* decisions;
* specifications;
* work history;
* artifacts;
* reviews;
* governance information;
* project knowledge.

Agent Runtime Memory may contain:

* sessions;
* conversations;
* runtime context;
* execution history;
* model interaction state.

A runtime may consume information from Engineering Memory as context.

A runtime's session history shall not automatically become authoritative Engineering Memory.

The mechanism for synchronizing or deriving engineering knowledge from runtime activity requires a future architectural decision.

---

# Consequences for Skills and Plugins

The existence of runtime-specific mechanisms such as skills, extensions or plugins does not automatically make them Engineering Core concepts.

Your Harness shall distinguish between:

* engineering-level capabilities;
* runtime-level capabilities;
* integration capabilities.

A future architectural decision shall determine whether YH skills and plugins are:

1. runtime-independent artifacts;
2. runtime-specific artifacts;
3. portable artifacts with runtime adapters;
4. or a combination of these models.

No final decision is made here.

---

# Consequences for Context

The Engineering Core may construct or provide engineering context required for agent execution.

The runtime remains responsible for managing runtime-specific execution context.

Therefore:

```
Engineering Context
       |
       v
Runtime Integration
       |
       v
Agent Runtime Context
```

The exact contract between Engineering Context and Runtime Context requires further definition.

---

# Non-Goals

This ADR does not:

* select Pi as the runtime;
* define the complete Agent Runtime API;
* define a native YH agent loop;
* define a runtime plugin system;
* define the final memory architecture;
* define the final skills architecture;
* define the final plugin architecture;
* define model-provider abstractions;
* define a session persistence format;
* implement any runtime integration.

These concerns require subsequent design work.

# Open Questions

The following questions remain intentionally unresolved:

1. What is the minimum capability contract required from an Agent Runtime?
2. Should the runtime execute individual Work Items or higher-level workflows?
3. How should YH construct engineering context for a runtime?
4. How should runtime events become engineering evidence?
5. How should Human in the Middle approvals interact with runtime execution?
6. Where should Skills be defined?
7. Where should Plugins be defined?
8. How should engineering memory be exposed to a runtime?
9. Should YH provide a native runtime?
10. Can Pi satisfy the future runtime contract without compromising YH's architectural independence?
11. Should runtime selection be project-level, workspace-level or execution-level?
12. How should runtime capabilities be discovered and negotiated?

These questions shall not be answered implicitly by implementation.

---

# Notes

This ADR establishes the architectural boundary, not the concrete runtime implementation.

The project should avoid implementing runtime abstractions solely on the assumption that Pi will be used.

The runtime contract should emerge from concrete engineering requirements and validated use cases.

Pi remains an important candidate for evaluation because it already provides substantial agent-runtime capabilities, but its adoption is intentionally left open.

---

# Decision Review

This ADR should be revisited when:

* the Agent Runtime contract is defined;
* a first runtime implementation is selected;
* Pi integration is implemented;
* a native runtime is considered;
* runtime state begins influencing Engineering State;
* or a significant change occurs in the project's execution model.
