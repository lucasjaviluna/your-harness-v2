# ADR-002 — Agent Runtime Boundary

**Document ID:** YH-ADR-002
**Version:** 1.0.0
**Status:** Proposed
**Release:** v0.1.0 Foundation / v0.2.0 Architecture

---

# Status

Proposed

---

# Context

Your Harness defines an engineering platform whose primary responsibility is to govern and support software engineering work.

The current repository contains two groups of responsibilities that are increasingly distinguishable:

### Engineering responsibilities

The domain and application layers currently model concepts such as:

* Intent
* Work Item
* Specification
* Review
* Release

These concepts represent engineering state, engineering decisions, governance and traceability.

### Execution responsibilities

The current runtime-oriented implementation contains:

* Agent execution
* Workflow execution
* Agent sessions
* AI model interaction
* AI provider connectors
* MCP
* Tools
* Skills
* Runtime context
* Runtime events
* Prompt construction

These capabilities are required to execute work but are not themselves the authoritative representation of engineering state.

The distinction becomes especially important when considering external agent runtimes such as Pi.

Pi may provide agent execution, sessions, tools, model interaction and runtime-specific capabilities. However, making YH's Engineering Core depend directly on Pi would couple the engineering model to a concrete execution technology.

The same problem would occur if the Engineering Core were coupled directly to the current native runtime implementation.

Therefore, Your Harness requires an explicit architectural boundary between engineering responsibilities and execution responsibilities.

---

# Decision

Your Harness shall maintain a conceptual and architectural boundary between the **Engineering Core** and the **Agent Runtime**.

The Engineering Core shall remain independent of any concrete runtime implementation.

The Agent Runtime boundary shall represent execution capabilities without prescribing a particular implementation.

A runtime implementation may be:

* a native YH runtime;
* Pi;
* another external runtime;
* or a future runtime implementation.

No concrete runtime is selected by this ADR.

Pi is therefore considered a **candidate runtime implementation**, not a mandatory dependency, core component, default runtime or exclusive runtime.

---

# Architectural Boundary

The architecture is defined conceptually as:

```text
                 YOUR HARNESS
                      │
        ┌─────────────┴─────────────┐
        │                           │
        ▼                           ▼
 ENGINEERING CORE             AGENT RUNTIME
        │                           │
        │                           │
        │                    Workflow execution
        │                    Agent execution
        │                    Sessions
        │                    AI models
        │                    Tools
        │                    MCP
        │                    Skills
        │                    Runtime context
        │                    Runtime events
        │
 Intent
 Work Item
 Specification
 Review
 Release
 Governance
 Engineering state
 Engineering traceability
        │
        └──────────────┬──────────────┘
                       │
                Runtime Boundary
```

The boundary is conceptual first.

The existence of the boundary does not require an immediate package split, interface hierarchy or directory restructuring.

# Engineering Core Responsibilities

The Engineering Core owns concepts and state that represent the engineering process itself.

The Engineering Core includes, but is not limited to:

* Project
* Intent
* Work Item
* Specification
* Review
* Release
* Engineering workflows
* Governance
* Approval requirements
* Engineering verification
* Engineering traceability
* Engineering decisions
* Engineering memory

The Engineering Core is the authoritative owner of engineering state.

Examples of engineering state include:

```text
Intent status
Work Item status
Specification status
Review status
Release status
Approval decisions
Governance decisions
Engineering artifacts
Engineering decisions
```

The Engineering Core determines:

> what engineering work exists, why it exists, what constraints apply, and what constitutes an accepted engineering outcome.

---

# Agent Runtime Responsibilities

The Agent Runtime owns mechanisms required to execute work.

The Agent Runtime includes, but is not limited to:

* Agent execution
* Workflow execution
* Agent sessions
* Model interaction
* AI provider integration
* Tool execution
* MCP integration
* Runtime skills
* Runtime context
* Runtime events
* Runtime prompts
* Runtime execution state

The Agent Runtime determines:

> how execution is performed.

The Runtime may execute an engineering Work Item, but it does not become the authoritative owner of that Work Item's engineering state.

---

# Work Item and Workflow Separation

A Work Item and a Workflow are different concepts.

A **Work Item** is an engineering unit of work.

A **Workflow** is an execution strategy.

Therefore, the domain must not assume that every Work Item owns or requires a specific Workflow.

Conceptually:

```text
Engineering Core

Intent
  │
  ▼
Work Item
  │
  │ execution request
  ▼
Runtime Boundary
  │
  ▼
Workflow / Execution Strategy
  │
  ▼
Runtime execution
```

A Work Item may be executed:

* manually;
* through an agent;
* through a workflow;
* through a future runtime;
* through another execution mechanism.

The existence of the current `WorkflowEngine` therefore does not justify introducing a mandatory `Workflow` relationship into the Work Item domain model.

---

# Engineering State and Runtime State

Engineering State and Runtime State are separate concepts.

## Engineering State

Examples:

```text
Intent
Work Item
Specification
Review
Release
Approval
Governance
Engineering artifacts
```

## Runtime State

Examples:

```text
Agent session
Conversation messages
Current model
Tool calls
Tool results
Runtime context
Execution steps
Runtime events
Iteration count
```

Runtime state must not automatically become engineering state.

A runtime session is not an engineering Work Item.

A tool call is not an engineering state transition.

A model response is not automatically an engineering decision.

A workflow result is not automatically a verification result.

---

# Runtime Results and Engineering Evidence

The Runtime may produce execution results such as:

```text
command output
test output
tool result
agent response
workflow result
execution error
```

These are runtime outputs.

They may later become inputs to engineering verification or engineering evidence, but this transformation belongs to the Engineering layer.

Conceptually:

```text
Runtime Output
      │
      ▼
Engineering Interpretation
      │
      ▼
Engineering Evidence
      │
      ▼
Engineering State
```

The Runtime must not independently decide that a runtime result constitutes an accepted engineering outcome.

---

# Governance and HITM

Governance belongs to the Engineering Core.

Human-in-the-middle requirements are therefore engineering constraints rather than runtime-owned policy.

The Runtime may provide mechanisms such as:

* pause;
* resume;
* confirmation;
* approval request;
* execution interruption.

However, the Runtime must not independently determine which engineering actions require approval.

Conceptually:

```text
Engineering Core
      │
      │ governance requirement
      ▼
Runtime Boundary
      │
      │ execution constraint
      ▼
Agent Runtime
```

The Engineering Core remains authoritative over approval requirements and engineering decisions.

---

# Runtime Independence

The Engineering Core must not directly depend on APIs, types, events or persistence mechanisms belonging to a specific runtime.

In particular, the Engineering Core must not depend directly on:

* Pi-specific APIs;
* Pi-specific session types;
* Pi-specific persistence;
* Pi-specific events;
* Pi-specific extension mechanisms;
* native runtime implementation details.

This rule applies equally to any future runtime.

The goal is not to make every runtime identical.

The goal is to prevent a runtime implementation from becoming the definition of the engineering model.

---

# Runtime Implementations

The architecture permits multiple runtime implementations:

```text
                  Engineering Core
                         │
                         ▼
                 Runtime Boundary
                         │
             ┌───────────┼───────────┐
             │           │           │
             ▼           ▼           ▼
       Native YH       Pi        Other Runtime
        Runtime       Runtime
```

The current runtime implementation may continue to evolve while this boundary is being established.

A native runtime is therefore not rejected.

Pi is not selected.

Other runtimes remain possible.

---

# Pi Integration

Pi is considered a potential Agent Runtime implementation.

If Pi is adopted, the expected architectural relationship would be:

```text
Your Harness
     │
     ├── Engineering Core
     │
     └── Runtime Boundary
              │
              ▼
         Pi Runtime
```

The Engineering Core must remain independent of Pi.

Pi integration should therefore occur at the Runtime Boundary rather than by introducing Pi dependencies into domain or application code.

This ADR does not decide whether Pi will ultimately be used.

---

# Memory Separation

Engineering Memory and Runtime Memory are distinct.

## Engineering Memory

Contains knowledge relevant to the engineering process, such as:

* decisions;
* specifications;
* work history;
* reviews;
* releases;
* engineering artifacts;
* project knowledge;
* governance information.

## Runtime Memory

May contain:

* sessions;
* conversations;
* execution history;
* runtime context;
* model context;
* compaction state;
* runtime-specific state.

Runtime memory may consume Engineering Memory as context.

However, runtime session history must not automatically become authoritative Engineering Memory.

---

# Skills and Plugins

The current repository contains skills and plugins that support runtime extensibility.

Their final architectural ownership is not decided by this ADR.

In particular, future architecture must determine whether:

* skills are runtime-specific;
* skills are portable across runtimes;
* plugins belong to YH's extension system;
* plugins belong to individual runtimes;
* YH provides adapters for runtime-specific extensions.

Until those decisions are made, no new abstraction should be introduced solely to accommodate a possible runtime.

---

# Context Separation

Context exists at multiple architectural levels.

Engineering Context may contain:

```text
Intent
Work Item
Specification
Governance
Relevant decisions
Acceptance criteria
Engineering constraints
```

Runtime Context may contain:

```text
Conversation
Model state
Tool state
Session state
Runtime instructions
Runtime-specific context
```

The precise contract between Engineering Context and Runtime Context is intentionally deferred.

The existence of this distinction does not require an immediate `EngineeringContext` or `RuntimeContext` abstraction.

---

# Specification Engine Independence

The Runtime Boundary is independent from the Specification Engine defined by ADR-001.

These are separate replaceability boundaries:

```text
Specification Engine
        │
        ├── OpenSpec
        └── Other specification framework

Runtime Boundary
        │
        ├── Native
        ├── Pi
        └── Other runtime
```

A specification framework and an execution runtime must not be treated as the same architectural concern.

---

# Consequences

## Positive Consequences

* Engineering concepts remain independent of execution technology.
* Pi can be evaluated without coupling YH to Pi.
* A native YH runtime remains possible.
* Alternative runtimes remain possible.
* Engineering state remains distinct from runtime state.
* Runtime memory does not automatically become engineering memory.
* Runtime experimentation can occur without redesigning the domain.
* The current runtime implementation can continue evolving while the boundary is clarified.

## Trade-offs

* A boundary introduces integration work.
* Runtime results may require explicit interpretation before becoming engineering evidence.
* Future runtime integrations may require adapters.
* Context exchange will require an explicit contract.
* Skills and plugins may require additional architectural decisions.
* Runtime and Engineering Core may evolve at different speeds.

---

# Non-Goals

This ADR does not:

* select Pi as the runtime;
* reject Pi;
* define a final `AgentRuntime` interface;
* define a final execution protocol;
* define a runtime session model;
* define runtime persistence;
* define Engineering Memory architecture;
* define Runtime Memory architecture;
* define Skills architecture;
* define Plugin architecture;
* define a native runtime implementation;
* define Pi integration;
* define model-provider architecture;
* define Engineering Context;
* define Engineering Evidence;
* introduce a mandatory Workflow relationship into Work Item.

# Notes

This ADR intentionally defines a boundary rather than an implementation.

The existence of a potential runtime such as Pi must not drive abstractions that are not otherwise justified.

The implementation should evolve from concrete responsibilities and use cases.

The architectural rule is therefore:

> **Do not introduce an abstraction merely because a runtime may need it. Introduce an abstraction when a real responsibility requires isolation or replacement.**

---

# Decision Review

This ADR should be revisited when one or more of the following occur:

* the first Runtime Boundary contract is defined;
* a concrete runtime is selected;
* Pi integration is implemented;
* a native runtime becomes a strategic requirement;
* runtime state needs to influence engineering state;
* runtime output needs to become engineering evidence;
* Skills or Plugins require cross-runtime portability;
* the execution model changes materially.
