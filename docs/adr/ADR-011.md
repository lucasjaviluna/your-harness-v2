# ADR-011 — Límite de escritura y sincronización con proveedores SDD

- **Estado:** Proposed
- **Fecha:** 2026-09-14
- **Decisión propuesta:** separar lectura SDD de materialización, conservar al proveedor como fuente de verdad y hacer explícitas las operaciones de escritura y sincronización.

## Contexto

El `SddProvider` actual es read-only y OpenSpec se proyecta desde el filesystem. La visión de your-harness requiere que el agente pueda analizar tareas, proponer Specifications/Changes y eventualmente materializar artefactos, pero una integración de escritura prematura podría mezclar tres responsabilidades:

- la semántica y formato propios de OpenSpec;
- la gobernanza HITM de your-harness;
- el estado operacional local de ejecuciones y verificaciones.

## Decisiones propuestas

### 1. Fuente de verdad

El proveedor SDD sigue siendo dueño de sus artefactos normativos y de su formato. Para OpenSpec, la fuente de verdad continúa siendo el árbol `openspec/`.

your-harness puede persistir bindings, decisiones HITM, snapshots, provenance, trazas y reportes de verificación, pero no replica ni reemplaza automáticamente las Specifications o Changes del proveedor.

### 2. Separación de ports

`SddProvider` permanece orientado a lectura:

```text
SddProvider
  → readProject
```

La escritura se expone mediante un port separado, inicialmente propuesto como `SddMaterializer`:

```text
SddMaterializer
  → createDraftChange
  → updateDraftChange
  → materializeApprovedChange
```

El port de materialización no será implementado por todos los proveedores. La capacidad debe descubrirse explícitamente y un proveedor read-only debe rechazarla de forma clara.

### 3. Alcance inicial de escritura

La primera capacidad de OpenSpec no debe modificar directamente una Specification aprobada. El alcance seguro inicial es:

1. crear un Change en estado draft/proposed;
2. escribir `proposal.md`, `design.md` y `tasks.md` mediante el adapter del proveedor;
3. leer y validar la proyección resultante;
4. devolver provenance y digest nuevos;
5. dejar la aprobación y la aplicación de efectos como pasos posteriores y explícitos.

Los cambios sobre `openspec/specs/**` se consideran una operación de mayor riesgo y requieren una capacidad separada, guardrail específico y aprobación HITM explícita.

### 4. Mecanismo de OpenSpec

Application no invoca comandos OpenSpec ni conoce rutas físicas. `OpenSpecMaterializer` encapsula el mecanismo real —CLI oficial, filesystem controlado o combinación— y debe verificar el resultado mediante una nueva lectura del `OpenSpecSddProvider`.

Hasta validar las capacidades reales del proveedor, no se asume que existe un CLI de escritura ni se inventa una interfaz de comandos.

### 5. Sincronización

La sincronización será explícita y unidireccional por operación:

```text
Proveedor → read/project  → your-harness
your-harness → materialize → proveedor
```

No habrá sincronización bidireccional automática ni actualización silenciosa de checklists. Después de materializar, el adapter debe releer y devolver la proyección observada. Si el resultado no coincide con lo solicitado, la operación falla y no se considera aprobada.

### 6. HITM y guardrails por etapa

Todas las etapas de un Change requieren aprobación explícita del usuario antes de avanzar. El agente puede analizar, generar alternativas y preparar previews, pero no puede promover una etapa ni aplicar sus efectos por sí solo.

Los checkpoints mínimos son:

1. **Proposal approval:** valida problema, objetivo, alcance y rationale.
2. **Design approval:** valida la solución técnica, límites, impactos, riesgos y decisiones arquitectónicas. Es obligatorio antes de materializar efectos sobre Specifications o iniciar implementación.
3. **Task-plan approval:** valida la descomposición del trabajo, orden, dependencias y criterios de verificación.
4. **Apply-readiness approval:** valida el delta final, el snapshot de los artefactos y que no existan cambios pendientes respecto de las etapas aprobadas.
5. **Verification/completion approval:** valida resultados, Evidence y autorización de cierre según ADR-009.

Si el usuario solicita cambios en cualquier etapa, el Change vuelve a revisión desde esa etapa y se invalidan las aprobaciones posteriores afectadas. En particular, un cambio de Design invalida el Task Plan y el Apply Readiness.

Se mantienen cuatro niveles de interacción:

| Operación | HITM | Resultado |
|---|---|---|
| Analizar o generar una etapa sin escribir | No, salvo política del proyecto | Preview inmutable |
| Aprobar y persistir una etapa del Change | Sí, aprobación de esa etapa | Artefactos versionados con digest |
| Materializar efectos sobre Specifications | Sí, Design y Apply Readiness aprobados | Efectos aplicados y releídos |
| Ejecutar, verificar y completar | Sí, según políticas de ejecución/verificación | Traces, Evidence y autorización |

Toda escritura debe pasar además por `ExecutionEnvironmentGuard`, declarar su capability y registrar actor, motivo, provenance anterior/nueva, digest y resultado.

La aprobación HITM debe quedar asociada a la etapa, al digest aprobado y a la versión del Change. Aprobar un Change no significa aprobar automáticamente sus etapas futuras ni sus modificaciones posteriores.

El contrato Application `ChangeStageApproval` representa esta decisión como un registro inmutable con `changeId`, `stage`, `changeVersion`, `changeDigest`, decisión, actor, rol, motivo e instante. `request-rework` y `reject` también se registran: no son errores técnicos, sino decisiones humanas que impiden avanzar y permiten retroalimentar la etapa.

`ChangeStageApprovalPolicy` evalúa si una etapa puede avanzar. Exige una decisión `approve` para la etapa solicitada y para todas las anteriores, con la misma versión y digest. Una decisión de rework/rechazo o cualquier mismatch bloquea el avance y devuelve razones estructuradas.

`ApproveChangeStageUseCase` es el punto de Application para registrar estas decisiones. Ningún comando, skill, agente o adapter debe persistir una aprobación directamente; todos deben pasar por este caso de uso y su policy.

### 7. Idempotencia y drift

Una materialización debe aceptar un snapshot/base digest cuando opere sobre un artefacto existente. Si el digest actual difiere del esperado, se rechaza la escritura y se requiere relectura, revisión y eventual reautorización.

Las operaciones deben ser idempotentes mediante una referencia de operación/correlación y, cuando el proveedor lo permita, escritura atómica o recuperación segura ante fallo parcial.

## Consecuencias

- Un proveedor read-only sigue siendo válido para consulta y ejecución gobernada.
- La capacidad de escribir es explícita, descubrible y protegible por policy.
- El agente puede preparar propuestas sin tener automáticamente permiso para modificar la fuente SDD.
- La aplicación de cambios sobre Specifications queda separada de la creación de un Change.
- El `TaskOrchestrator` futuro coordinará estos ports, pero no conocerá OpenSpec ni sus comandos.

## Preguntas para aceptar el ADR

1. ¿Aceptamos `SddMaterializer` como port separado de `SddProvider`?
2. ¿El primer alcance debe limitarse a crear/actualizar Changes draft?
3. ¿Confirmamos que cualquier escritura persistente requiere confirmación HITM, incluso si sólo crea un draft?
4. ¿La aplicación sobre `openspec/specs/**` debe quedar fuera del primer vertical slice?
5. ¿Confirmamos que una modificación posterior de Design invalida obligatoriamente Task Plan y Apply Readiness?
