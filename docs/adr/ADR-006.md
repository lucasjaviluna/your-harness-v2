# ADR-006 — SDD Change Boundary and Provider Contract

- **Status:** Proposed
- **Date:** 2026-09-12

## Context

ADR-001 makes Specification Engines replaceable. ADR-003 defines the normalized
behavioral model that they can produce: `Specification → Requirement → Scenario`.

An SDD workflow also distinguishes the system's current behavioral truth from a
proposed evolution. OpenSpec calls the latter a change and associates it with a
proposal, specification deltas, an optional design, and implementation tasks.

YH needs to preserve that distinction without making OpenSpec's folders, Markdown
files, or task syntax part of its domain. It also needs a boundary through which a
provider can expose its artifacts to the Engineering Core. Without that boundary,
future persistence or guardrails would either duplicate an external source of truth
or couple the Core to a single SDD tool.

## Decision

### 1. A Change is proposed engineering evolution, not current truth

YH recognizes an engineering **Change** as a coherent proposed evolution motivated
by an `Intent`. It is distinct from a `Specification`:

```text
Intent
  └── Change (proposed evolution)
        ├── specification effects / deltas
        ├── design material
        └── implementation tasks

Current Specification (authoritative behavior)
```

An approved, applied change may update the current Specification. Until then, it
does not replace it.

`Change` is a first-class engineering concept, but this ADR does **not** introduce a
YH `Change` domain aggregate, persistence schema, or universal lifecycle. Those
would be premature until YH needs to own cross-provider change governance. For now,
a provider exposes a normalized *change descriptor* at the Application boundary.

### 2. Preserve semantic roles instead of provider artifacts

The following roles are kept separate:

| SDD concern | YH responsibility |
|---|---|
| Why a change exists | `Intent` and change rationale |
| Current required behavior | `Specification → Requirement → Scenario` |
| Proposed behavioral modification | Change specification effects/deltas |
| How to achieve it | Design material / engineering decisions |
| Implementation breakdown | Provider tasks and YH work planning |
| Execution | Application use cases and RuntimePort |

Provider-specific paths, Markdown names, task checkboxes, and lifecycle labels are
not domain properties. They remain provider details and can be retained only as
opaque provenance references at the Application boundary.

### 3. Provider tasks inform planning; they are not domain relationships

A `WorkItem` remains a YH Engineering Core unit tied to an `Intent`. A provider task
is provider-owned implementation-planning material inside a Change. Neither is a
subtype, direct alias, or required persisted relation of the other.

The Application layer may select one or more provider tasks while planning an
execution. It combines their executable intent with the authoritative Specification
and the relevant WorkItem, then projects only neutral execution data across the
Runtime Boundary:

```text
WorkItem + selected provider task material + approved Specification
                         │
                         v
                   Application use case
                         │
                         v
ExecutionRequest { objective, EngineeringContext, executionConstraints }
                         │
                         v
                       Runtime
```

The Runtime does not receive `WorkItem`, provider task types, provider identifiers,
or domain aggregates. A future trace record may associate a WorkItem, a Change
reference, and selected task references for observability, but that record belongs to
Application/infrastructure and is not a WorkItem domain relationship.

This ADR does not decide task synchronization behavior, the trace-record shape, or
whether every Change must have a persisted YH representation.

### 4. SddProvider is an Application port

YH will introduce an `SddProvider` port in the Application layer when the first
concrete use case is implemented. Its minimum responsibility is to read a project
through an SDD provider and project it into neutral Application data:

```text
SddProvider
  ├── identifies the provider and project scope
  ├── exposes current specification material
  ├── exposes proposed change descriptors and provenance
  └── projects normative Requirements and Scenarios to the YH model
```

The port must not:

- expose OpenSpec, Spec Kit, or runtime-specific types to the domain or runtime;
- create or mutate `WorkItem` aggregates implicitly;
- determine engineering approval, completion, evidence, or guardrail outcomes;
- require a provider CLI to be installed when reading is sufficient;
- own persistence of YH operational state.

Writing artifacts, invoking provider CLIs, task synchronization, and archiving are
separate use cases. They will be added only when a concrete workflow requires them.

### 5. Provenance is explicit but opaque

Application-level projections may include a stable provider identifier and a
provider-owned change/artifact reference. This preserves traceability while keeping
the YH domain neutral:

```text
provider id + external reference
        ↓
normalized Change descriptor / Specification projection
        ↓
Engineering Core and Application use cases
```

The Runtime never receives provider provenance unless a future execution use case
requires a neutral, approved representation of it.

## Implementation status

The first physical contract is implemented in `packages/application/src/sdd/` and
the first adapter is `src/sdd/openspec/OpenSpecSddProvider`. The adapter is a
read-only local-filesystem spike: it projects current OpenSpec specifications and
proposed changes without invoking an OpenSpec CLI, writing artifacts, synchronizing
tasks, or creating Domain aggregates. The lifecycle and write-related non-goals of
this ADR remain open.

Application also provides an in-memory `ExecutionTrace` record that can associate a
provider Change/task provenance with a Specification, WorkItem and RuntimeResult.
It is operational observability only; it is not a WorkItem relationship, a Change
lifecycle, evidence, or persistent storage implementation.

## Consequences

### Positive

- Separates current behavioral truth from proposed changes.
- Avoids equating WorkItems with external task checklists.
- Gives OpenSpec and future providers a concrete, narrow integration boundary.
- Allows future guardrails to evaluate traceability without putting provider logic
  into the runtime.
- Avoids prematurely freezing a universal Change lifecycle or persistence model.

### Trade-offs

- The first provider integration needs a projection layer before it can drive YH.
- Work planning needs an Application projection before provider tasks can influence
  an execution, even though neither object crosses the Runtime Boundary.
- Provider artifacts are not automatically writable or executable from YH.

## Explicit Non-Goals

This ADR does not decide:

- a `Change` domain aggregate or status lifecycle;
- a universal provider API beyond the initial read-only `SddProvider` contract;
- a Spec Kit or native adapter implementation;
- artifact generation, mutation, archiving, or provider CLI invocation;
- persistence of changes, operational state, or mappings;
- task synchronization;
- verification or evidence;
- guardrail policy details.

## Relationship with Previous ADRs

- **ADR-001:** `SddProvider` operationalizes the replaceable Specification Engine
  boundary without selecting a permanent provider implementation.
- **ADR-003:** current specifications remain the normalized behavioral source of
  truth; changes project Requirements and Scenarios without importing provider
  artifacts into the domain.
- **ADR-004 / ADR-005:** the Runtime receives only an approved `ExecutionRequest`
  and contextual engineering knowledge. It does not inspect changes or providers.

## Future Decisions

1. First physical `SddProvider` contract and read-only provider spike.
2. Work-planning use case and optional Application-level execution trace record.
3. Change lifecycle and whether/when YH owns it as a domain aggregate.
4. Project-local operational persistence.
5. Guardrail policies at specification, design, execution, and runtime levels.

## Decision Summary

YH distinguishes proposed SDD changes from current specifications. A future
Application-level `SddProvider` projects provider artifacts into neutral change and
specification representations. The domain and Runtime remain independent of OpenSpec
or any other SDD tool.
