# ADR-005 — Engineering Context

- **Status:** Accepted
- **Date:** 2026-09-11

## Context

The Engineering Core needs to provide a runtime with the engineering knowledge required to execute a WorkItem. The runtime must not receive Domain aggregates directly, and the contextual information needed for execution must remain independent from any concrete runtime such as Pi.

A distinction is required between engineering knowledge and runtime instructions. Engineering knowledge describes what the system needs to know; runtime instructions describe how the runtime should conduct the execution.

Future retrieval mechanisms such as RAG may help select relevant knowledge, but the retrieval mechanism itself must not become part of the context contract.

## Decision

`EngineeringContext` is an Application-level representation of the relevant engineering knowledge selected for a specific execution.

```text
EngineeringContext
├── knowledge
├── requirements
└── engineeringConstraints
```

### Knowledge

`knowledge` contains supporting engineering information relevant to the execution. It is contextual information and is not itself an authoritative Domain aggregate.

### Requirements

`requirements` contains the normative engineering behavior relevant to the execution.

```text
Requirement
├── name
├── normative statement
└── scenarios
      ├── condition
      └── expected behavior
```

The Application representation must not expose Domain entities directly across the Runtime Boundary.

### Engineering Constraints

`engineeringConstraints` contains implementation constraints that the runtime must respect while performing the requested work.

These constraints are engineering context, not runtime-specific instructions.

### Context versus Instructions

`EngineeringContext` represents what the runtime needs to know.

It does not contain:
- prompts;
- agent instructions;
- runtime-specific configuration;
- Pi-specific types;
- RAG implementation details;
- guardrail mechanisms;
- Domain aggregates.

Runtime instructions remain part of the execution request/runtime interaction.

### Context versus Engineering Memory

`EngineeringContext` is an execution-specific selection of engineering knowledge. It is not the authoritative engineering memory store.

The Engineering Core remains the source of truth for specifications, requirements, decisions, project knowledge and other engineering artifacts.

### RAG

RAG is considered a possible retrieval mechanism for constructing an `EngineeringContext`.

RAG is therefore not part of the `EngineeringContext` model and does not define its contract.

The specific retrieval strategy will be decided separately if and when a real use case requires it.

### Runtime Boundary

The Application layer provides the context through `ExecutionRequest`:

```text
Engineering Core / Application
        ↓
EngineeringContext
        ↓
ExecutionRequest
        ↓
RuntimePort
        ↓
Concrete Runtime
```

The concrete runtime may be Pi, the native YH runtime, or another runtime. No concrete runtime dependency is introduced by this decision.

## Consequences

### Positive

- Keeps engineering knowledge independent from runtime implementation.
- Prevents Domain entities from leaking across the Runtime Boundary.
- Preserves the distinction between engineering knowledge and runtime instructions.
- Allows different runtimes to consume the same execution contract.
- Leaves room for RAG without coupling the architecture to a particular retrieval technology.
- Keeps the context model small and focused.

### Negative

- The Application layer needs a projection from Domain concepts into the neutral context representation.
- A future retrieval mechanism will need a defined policy for selecting the appropriate engineering context.
- Runtime-specific prompt construction remains the responsibility of the runtime side.

## Explicit Non-Goals

This ADR does not decide:
- the concrete implementation of a Context Builder;
- RAG architecture or technology;
- vector databases or embedding models;
- persistence of engineering memory;
- prompt construction;
- runtime-specific context formats;
- guardrail implementation;
- verification or evidence models;
- OpenSpec adapters;
- runtime selection;
- Pi integration details.

Those decisions require their own concrete use cases and architectural decisions.

## Relationship with Previous ADRs

### ADR-001 — Specification Engine Abstraction

The Specification Engine remains independent from `EngineeringContext`. An implementation such as OpenSpec may provide the engineering specifications from which contextual requirements are projected.

### ADR-003 — Engineering Specification Model

`EngineeringContext` consumes the relevant engineering requirements and scenarios defined by the Engineering Specification Model. It does not replace the Specification model.

### ADR-004 — Runtime Boundary and Execution Contract

`EngineeringContext` is carried by `ExecutionRequest` across the Application Runtime Boundary. The runtime consumes the context but does not own its engineering authority.
