01 · Qué es

Un harness de desarrollo con IA, gobernado por ingeniería

«Your Harness existe para mejorar la forma en que el software es ingenierizado. La planificación, las especificaciones, la gobernanza y el juicio humano son ciudadanos de primera clase. La IA acelera la ingeniería, pero permanece bajo supervisión humana explícita.» — YH-VISION-001

Your Harness es una herramienta CLI que orquesta agentes de IA, plugins, skills, servidores MCP y flujos de trabajo para el desarrollo de software. A diferencia de las herramientas convencionales de "code generation", no se enfoca en generar código: se enfoca en gobernar el proceso de ingeniería — desde la intención original hasta el release.

Es agnóstico a proveedores de IA (Claude, OpenAI, Copilot, Ollama, custom), extensible por diseño mediante plugins y skills, y estructura todo el trabajo alrededor de un modelo de dominio explícito: Intent → Work Item → Specification → Review → Approval → Implementation → Verification → Release.

🧩

Modular y reemplazable

Cada responsable del sistema —specs, runtimes, proveedores, plugins— se integra detrás de abstracciones estables.

🎯

Spec-driven

Nada se implementa sin una especificación aprobada que describa el comportamiento esperado.

🧭

Human in the Middle

La automatización asiste, pero la responsabilidad y la aprobación de decisiones críticas siempre pertenecen a personas.

02 · Objetivo

El objetivo central del proyecto es transformar el desarrollo de software en un proceso estructurado, transparente y gobernado, donde la calidad emerge de prácticas de ingeniería disciplinadas en lugar de la velocidad de generación de código.

📉

Reducir la ambigüedad

Especificaciones y un lenguaje de dominio común (YDL) eliminan interpretaciones vagas durante el desarrollo.

🔍

Decisiones trazables

🔄

Componentes reemplazables

Engines, runtimes y proveedores intercambiables sin rediseñar el modelo de ingeniería.

👥

Humano en control

🧭

Disciplinas múltiples

📐

04 · Arquitectura

Dos dominios, un solo sistema

El repositorio convive con dos codebases con arquitecturas distintas y complementarias. La separación entre Engineering Core (qué trabajo de ingeniería existe, por qué existe y qué es aceptable) y el Agent Runtime (cómo se ejecuta el trabajo) es la columna vertebral del diseño, formalizada en ADR-002.

🧠 Engineering Core — el estado autoritativo

  • Intent — el resultado deseado por el usuario
  • Work Item — la unidad de trabajo gobernada
  • Specification + Requirement + Scenario — comportamiento esperado
  • Review / Approval — evaluación y autorización
  • Release — incremento estable publicado
  • Governance — aprobaciones y trazabilidad

⚙️ Agent Runtime — el mecanismo de ejecución

  • Agents — loop de razonamiento con herramientas
  • Workflows — DAG de 8 tipos de steps
  • AI Providers — Claude, OpenAI, Copilot, Ollama, custom
  • MCP — clientes y servidores JSON-RPC
  • Skills — templates y herramientas por categoría
  • Plugins — extensión con hooks de ciclo de vida

05 · Flujo de trabajo

El flujo de ingeniería gobernado

Definido en RFC-001 y YGov, todo el trabajo de ingeniería avanza por etapas explícitas. Ninguna etapa se omite cuando la gobernanza lo exige, y cada una produce artifacts versionados.

EtapaRolArtifact que produce
Intent Resultado deseado en lenguaje natural; captura qué, no cómo. Intención registrada
Work Item Unidad mínima de trabajo gobernada — feature, bug fix, refactoring, deuda técnica, doc, testing. Work Item
Specification Comportamiento esperado antes de implementar; con Requirements y Scenarios (ADR-003). Spec + Requirement + Scenario
Review Evaluación formal de corrección, claridad, consistencia y cumplimiento de estándares. Review
Approval Autorización explícita para avanzar a implementación, cuando la gobernanza lo requiere. Approval
Implementation Transforma la spec aprobada en artifacts ejecutables, consistente con la spec. Código + tests
Verification Confirma que la implementación satisface la spec: revisión manual, tests, criterios de aceptación. Evidencia de verificación
Release Publica los artifacts revisados y verificados como un incremento estable. Release
🔗

Trazabilidad de extremo a extremo

Cada implementación es rastreable a su Intent → Work Item → Specification → Review → Approval, cumpliendo la cadena definida en ADR-003.

🛡️

Gobernanza en el Core, no en el runtime

El runtime puede ofrecer pause/confirmación, pero jamás decide qué acciones de ingeniería requieren aprobación. Eso es del Engineering Core.

El contrato mínimo que cruza la frontera es un ExecutionRequest con objective · workspace · engineeringContext · executionConstraints, y devuelve un RuntimeResult con status · summary · runtimeSessionId · timestamps · failure. Conceptos como WorkItem no cruzan la frontera: la capa de aplicación los contextualiza.

🏷️

Una sola fuente de verdad

La spec (con sus Requirements/Scenarios) es la fuente autoritativa; el EngineeringContext es una proyección read-only para una ejecución concreta.

🔒

Estado separado

Un runtime session no es un Work Item; un tool call no es una transición de estado de ingeniería; un resultado del runtime no es evidencia de ingeniería sin interpretación.

🔧

Adapters como aislantes

Las implementaciones concretas (Harness, WorkflowEngine, AgentRunner, AIManager, MCPManager, Pi AgentSession) viven detrás de adapters que no filtran conceptos al Core.

📐

Replaceability

Spec Engine y Runtime Boundary son fronteras independientes: cambiar de framework de especificación no toca el runtime, y viceversa.
